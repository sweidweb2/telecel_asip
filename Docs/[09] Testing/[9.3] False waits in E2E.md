# False waits in E2E

## What this means

A **false wait** is when a test sits and waits for something that will never show up — usually because the assert no longer matches the real UI, or the step never completed.

The test is not “slow because the app is slow.” It is slow because it **waits until a long timeout**, then fails.

```
Right assert  → see result → continue (fast)
Wrong assert  → wait… wait… FAIL (feels slow)
```

## Why it matters

- Timeouts are often 20s, 60s, or 120s per wait.
- One stuck test can block a worker for minutes.
- A few false waits make the whole suite feel much larger than it is.

## How to avoid them

1. Assert what the **user sees now** (dialog, heading, URL) — not an old detail (toast vs dialog).
2. Prefer **short, clear waits** after each step. Fail early with a useful error.
3. When a run is “slow,” check failed tests first: long times next to ✘ usually mean a false wait.
4. Keep heavy journeys in E2E; put pure logic in unit tests.

## Local commands (DB-aware)

Connected to a shared or production DB? Prefer read-only runs:

| Command | What it does |
| --- | --- |
| `npm run test:e2e` | Smoke only (default) — no intentional writes |
| `npm run test:e2e:readonly` | Full suite minus `@writes` |
| `npm run test:e2e:full` | Everything — **can write** (use a non-prod DB) |

Auth setup logs in as existing editor/admin/viewer only. It does **not** create users.
